# Архитектурные и ML решения проекта Ames Housing

В данном документе зафиксированы ключевые идеи, методологии и архитектурные решения, принятые в процессе разработки ML-пайплайна для оценки стоимости недвижимости.

## 1. Методология разработки (MLOps & GitFlow)
* **Разделение Research и Production:** Jupyter Notebooks (`notebooks/`) используются исключительно как артефакты исследования (EDA, проверка гипотез, подбор параметров). Весь финальный код рефакторится в production-ready классы и скрипты (`src/`).
* **CI/CD и GitFlow:** Разработка ведется осознанно. Новые фичи (EDA, новые модели) делаются в ветках `feature/*`. После завершения этапа создается Pull Request в `develop`. Релиз в `main` происходит только когда готов бэкенд на FastAPI.
* **Тестирование (TDD):** Логика препроцессинга покрывается модульными тестами (`pytest`), чтобы предотвратить поломку пайплайна при дальнейших доработках.

## 2. Борьба с утечкой данных (Data Leakage)
**Проблема:** Применение трансформаций (например, вычисление среднего для скейлера) ко всему датасету до его разбиения приводит к завышенным метрикам и падению качества на проде.
**Решение:**
1. Строгий порядок при обучении: `train_test_split` -> Очистка `train` -> `preprocessor.fit(train)` -> `preprocessor.transform(train/test)`.
2. Очистка строк (удаление аномалий, дубликатов) вынесена **за пределы** трансформеров признаков, чтобы не ломать размерности матриц `X` и `y`.

## 3. ООП Архитектура препроцессинга (SOLID)
**Проблема:** Линейные модели (Lasso/Ridge) требуют `StandardScaler` и `OneHotEncoder`. Деревянные модели (CatBoost) инвариантны к масштабу и умеют работать со строками напрямую. Писать логику в одном классе через `if/else` — путь к нечитаемому коду (Spaghetti code).
**Решение:** 
Применен паттерн "Шаблонный метод" (Template Method) на базе абстрактного класса `BaseDataPreprocessor`:
* Реализован единый интерфейс `.fit()` и `.transform()`.
* Общая логика (заполнение пропусков, отбор фичей) реализована в базовом классе.
* Созданы классы-наследники `LinearDataPreprocessor` и `CatBoostDataPreprocessor`, которые переопределяют только специфичные методы (`_encode_categories_specific`, `_scale_specific`).

## 4. Train-Serve Skew и UX в FastAPI (Заполнение пропусков)
**Проблема:** В датасете ~80 признаков. Заставлять пользователя вводить их все на фронтенде — плохой UX. Однако если заполнять непереданные (опциональные) поля случайными константами (например, "Missing"), CatBoost на инференсе выдаст неадекватный результат, так как не видел этой категории при обучении (Train-Serve Skew).
**Решение (Стратегия умной импутации):**
В FastAPI (Pydantic) выделено **всего 5 обязательных полей** с максимальной предсказательной силой: `GrLivArea`, `OverallQual`, `YearBuilt`, `LotArea`, `OverallCond`. Остальные поля сделаны `Optional`.
Препроцессор обрабатывает отсутствующие данные (`None`) по 3 сценариям:
1. **Логическое отсутствие:** Поля, где отсутствие означает отсутствие объекта (площадь бассейна, гаража), заполняются нулем (`0`).
2. **Неизвестные числа:** Заполняются **медианами**, которые препроцессор запомнил во время обучения на `train`.
3. **Неизвестные категории:** Заполняются **модами** (самыми частыми значениями), запомненными во время обучения на `train`.

## 5. Выбор и обучение моделей
**Проблема:** Выбор оптимального алгоритма для табличных данных.
**Решения:**
* **Baseline (Линейные модели):** `ElasticNet` с подбором параметров (`GridSearchCV`) показал хорошую метрику (MAPE ~12.4%), выявив, что практически все признаки из отобранных полезны (слабая L1 регуляризация).
* **Champion (Градиентный бустинг):** `CatBoost` "из коробки" показал превосходство над линейной моделью (MAPE ~10.7%). Принято решение не использовать OHE для CatBoost, позволив алгоритму самостоятельно находить нелинейные зависимости в сырых строковых признаках.
* **Таргетирование метрики:** Зафиксирована разница между `eval_metric` (индикатор для Early Stopping) и `loss_function` (математическая функция, которую минимизирует алгоритм).

## 6. Упаковка артефактов
Принято железное правило: **Модель и её Препроцессор — это единый неделимый механизм.** 
В папку `models/` (добавленную в `.gitignore`) всегда сохраняются оба артефакта (например, `catboost_model.cbm` и `catboost_preprocessor.pkl`), что обеспечивает 100% воспроизводимость логики подготовки данных на бэкенде FastAPI.
